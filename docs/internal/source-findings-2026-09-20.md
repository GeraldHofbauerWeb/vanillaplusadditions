# Quelltext-Befunde aus dem Doku-Audit (2026-09-20)

Beim Gegenlesen der 47 Modulseiten haben die Prüf-Agenten nicht nur die Doku geprüft, sondern
auch gemeldet, was ihnen **im Java selbst** aufgefallen ist. Nichts davon wurde angefasst — das
hier ist eine Fundliste, keine Änderung.

**Vor dem Umsetzen jeweils selbst nachprüfen.** Die Befunde sind mit Datei und Zeile belegt und
haben sich in den Stichproben als zuverlässig erwiesen, aber ein Agent kann irren, und ein
Kommentar, der falsch *klingt*, ist manchmal nur knapp formuliert.

Insgesamt **39 Befunde** in **13 Modulen**.

## `chunk_reset`

- ChunkResetModule.java:189-192 — the radius==0 branch prints the green "✓ Chunk […] reset." unconditionally and ignores the `succeeded` counter computed at :180-185, so a single-chunk reset whose write threw still reports success in chat (the error only reaches the log at :215).
- ChunkResetModule.java:36 + :144 — `PendingReset(ChunkPos center, int radius)` does not record the dimension; `executeConfirm` applies the stored coordinates to `source.getLevel()` at confirm time, so confirming after a dimension change deletes the same ChunkPos in the wrong level.
- ChunkResetModule.java:138-142 — dead guard: `if (!(source.getLevel() instanceof ServerLevel serverLevel))` can never fail, because `CommandSourceStack.getLevel()` is declared `public ServerLevel getLevel()` (CommandSourceStack.java:398-400). The failure message "This command can only be used in a server level." is unreachable.
- ChunkResetModule.java:201-218 — the deletion is not durable: the module neither unloads the chunk nor flushes the IOWorker, and `ChunkMap.save` reaches the same `this.write(chunkpos, compoundtag)` (ChunkMap.java:790-792) for any still-loaded chunk with `isUnsaved() == true` (ChunkMap.java:770-772), so the next autosave (MinecraftServer.java:939-947, interval `Math.max(100, tickrate*300)` = 6000 ticks at 20 tps) writes the chunk straight back over the cleared entry.
- ChunkResetModule.java:206 — wrong/overbroad comment: "Remove any forced loading ticket first". `ServerLevel.setChunkForced(x, z, false)` removes only vanilla's `/forceload` ticket (ServerLevel.java:1415-1434); NeoForge/mod chunk tickets, spawn chunks and player tickets are untouched.
- ChunkResetModule.java:170-174 — the player rescue teleport keeps the old Y (`nearby.getY()`) and does no ground/collision search; `ServerPlayer.teleportTo(double,double,double)` is a plain `connection.teleport(…)` (ServerPlayer.java:1524-1526), so a player can be placed inside stone or in mid-air, and can immediately walk back into the square.
- ChunkResetModule.java:85 — a second `/chunkreset` silently replaces the pending entry via `Map.put`, and nothing ever expires or clears an entry on logout; only the newest square can be confirmed.

## `glider_water_repair`

## `idle_gamerules`

- IdleGamerulesModule.java:59-60 — the INFO line reports the full configured list as applied no matter what happened: performPrefixedCommand hands a parse failure to CommandSourceStack.sendFailure (Commands.java:321-346), which the withSuppressedOutput source drops (CommandSourceStack.java:510-514, silent=true per CommandSourceStack.java:236-255), and the module never inspects a return value. A typo or a rule from an absent mod is logged as a success. (The page documents this; listing it here as the underlying defect.)
- IdleGamerulesModule.java:32-50 — no restore path: the module has exactly one handler (ServerTickEvent.Post) and no ServerStopping/shutdown hook, while gamerules are persisted to level.dat (PrimaryLevelData.java:261). A server stopped, crashed or disabled while empty keeps doDaylightCycle=false / doWeatherCycle=false (+doSeasonCycle) with nothing left to undo them.
- IdleGamerulesConfig.java:29-32 — the defineList element validator is `o -> o instanceof String`, so an empty string or any typo passes config validation and only fails later as an unparseable command; a cheap guard (non-blank, matches a gamerule name pattern, or a warn log on a command that did not parse) would turn a silent no-op into a startup warning.

## `mo_arrows`

- FireArrowItem.asProjectile (src/main/java/net/geraldhofbauer/vanillaplusadditions/modules/mo_arrows/item/FireArrowItem.java:43-48) is dead code: a dispenser only fires items that have a registered DispenseItemBehavior (DispenserBlock.java:114, default DefaultDispenseItemBehavior; DispenseItemBehavior.java:73-75 registers only ARROW/TIPPED_ARROW/SPECTRAL_ARROW). The module never calls DispenserBlock.registerProjectileBehavior(FIRE_ARROW), so a dispenser drops the Fire Arrow as an item. Fix: register the behaviour in a FMLCommonSetupEvent enqueueWork block.
- MoArrowsModule.java:111-112 plays SoundEvents.FLINTANDSTEEL_USE with FlintAndSteelItem's pitch formula although the class javadoc and the docs describe the handler as mirroring a fire charge; FireChargeItem.java:63-68 uses SoundEvents.FIRECHARGE_USE with a different pitch. Either sound is defensible, but code and comment disagree.
- Disabling the module in the config unregisters the item (ModuleManager.java:95-107 / AbstractModule.java:90-101 skip onInitialize, so MoArrowsModule.java:74 never registers ITEMS), which silently destroys already-crafted Fire Arrows. This is the project-wide module pattern rather than a bug introduced here, but it is worth knowing for an item-adding module - the `light_fires` switch is the safe way to defuse the arrow.

## `mob_drops`

- MobDropsModule.java:34-38 - the field javadoc is wrong: it says 'Cache structure: EntityType -> (Item -> DropInfo)' while the field is `Map<EntityType<?>, List<DropInfo>>`. Leftover from the `Map<Item, Float>` predecessor in WitherSkeletonModule (v0.12.0^ WitherSkeletonModule.java:53); the list form is exactly what allows the same item twice per mob, so the comment describes the behaviour the code no longer has.
- MobDropsModule.java:96-104 - unreachable null check with a silent wrong-mob fallback: `BuiltInRegistries.ENTITY_TYPE` is a `DefaultedRegistry` with default key "pig" (BuiltInRegistries.java:141-143) and `DefaultedMappedRegistry.get(ResourceLocation)` is `@Nonnull`, returning `defaultValue.value()` (DefaultedMappedRegistry.java:55-60). So `if (mobType == null)` never fires, the 'Mob not found' warning can never print, and a typo'd mob id silently attaches the rule to `minecraft:pig`. Fix as in MobGlowModule.java:174 / :211, which calls `BuiltInRegistries.ENTITY_TYPE.containsKey(id)` first.
- MobDropsConfig.java:50-54 - `Float.parseFloat` accepts "NaN": the range test `chance < 0.0f || chance > 1.0f` is false for NaN, so `...;NaN` passes the spec validator, then `nextFloat() < NaN` is always false at runtime (MobDropsModule.java:153) and the rule silently never fires. Same silent-failure class as `chance = 0.0`, but this one looks like a typo rather than an intent.

## `waystone_amethyst_repair`
